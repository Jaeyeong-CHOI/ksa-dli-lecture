# 에이전틱 코딩 실습

k-skill 기존 Skill 활용 → Skill Creator로 공공데이터 API Skill 제작 → 화면 검증 → Vercel MCP 배포.

웹 안내: https://ksa.dli-lecture.com/agentic-coding

기본 ZIP은 READ_ME.md, PROMPTS.md, EXAMPLES.md 세 파일입니다. 실제 API 응답과 참고 화면은 웹에서 따로 열 수 있습니다. 예시를 받는 것과 Skill 설치·실행은 다릅니다.

실행 환경: ChatGPT 웹 Work와 Skills/Create가 제공되는 계정, 해당 작업의 Node.js/npx·Python 실행 환경, Vercel 계정. 실제 화면은 계정과 제품 변경에 따라 달라질 수 있습니다. 데스크톱 수동 MCP 설정은 선택 경로입니다.

검수 범위: 웹 Work에서 두 Skill의 계정 등록을 확인했고, 등록된 GeekNews Skill로 최신 조회·키워드 검색·상세 조회와 원문 대조를 마쳤습니다. Skill Creator는 국가유산 Skill을 만들고 검사했습니다. 국가유산 API는 Chrome에서 정상 XML을 받았으나 웹 에이전트 실행 환경은 502여서 첨부 응답 검증과 구분합니다. Vercel은 공식 플러그인 설치·로그인 경로를 확인했으며 이메일 인증 이후의 도구 조회·배포·재배포는 아직 검증하지 않았습니다.

## 1. 요청·Skill·MCP 큰 그림

페이지 하나를 만들고 배포할 때 각 요소가 맡는 일을 구분합니다.

실행 위치: 이 페이지 · 개념 설명과 예시 탐색

1. 아래 항목을 눌러 프롬프트·LLM·Skill·도구·MCP·Vercel의 역할을 비교합니다.
2. 실행 흐름의 1–4를 눌러 파일 생성과 배포가 어디서 달라지는지 봅니다.
3. 짧은 확인 문제를 풀고 준비 단계로 이동합니다.

성공 확인:
- Skill은 반복 절차, MCP는 외부 기능과 주고받는 규칙이라고 설명할 수 있습니다.
- 파일 생성과 웹 배포를 구분할 수 있습니다.
- 둘을 항상 함께 써야 하는 것은 아님을 이해했습니다.

막혔을 때: 모든 기능을 “GPT가 한다”로 묶지 말고, 누가 내용을 생각하고 누가 실제 기능을 실행하는지 나누어 보세요.

### Skill은 작업 설명서, MCP는 외부 도구와 대화하는 규칙입니다.

“문화유산 정보를 찾아 페이지로 보여 줘.” 정보 조회·응답 확인·화면 생성·배포는 서로 다른 일입니다. 에이전트는 필요한 절차와 도구를 골라 결과를 확인합니다.

직원에게 업무를 맡긴다고 생각해 보세요. 프롬프트는 이번 주문, Skill은 반복 업무 매뉴얼, 도구는 실제 업무 기능입니다. MCP는 다른 시스템의 기능을 찾아 요청하고 결과를 받기 위한 공통 약속에 가깝습니다.

### 프롬프트

이번에 원하는 결과와 재료를 전달합니다.

매번 달라지는 요구사항을 담습니다. Skill이 있어도 이번 작업의 입력은 필요합니다.

이번 실습: 입력 A: 경복궁 정보를 만들어 줘.

### LLM / 에이전트

요청을 이해하고 다음 행동을 고릅니다.

LLM은 글과 코드를 생성합니다. 에이전트는 앱 안에서 도구의 실행 결과를 보고 다음 작업도 이어 갑니다. 모델이 직접 인터넷 서버가 되는 것은 아닙니다.

이번 실습: 검색어 해석 → API 호출 → JSON 확인 → 화면 작성 → 요청받으면 배포.

### Skill

여러 작업에서 다시 쓸 절차와 확인 기준을 제공합니다.

매번 “없는 사실은 만들지 말기, 화면 확인하기…”를 반복해서 적는 부담을 줄입니다. 정해진 절차를 읽는 것이지 모델 가중치를 새로 학습시키는 것은 아닙니다.

이번 실습: heritage-brief: 검색어 → 공식 목록·상세 → 출처가 있는 JSON.

### 도구 · Tool

파일 저장, 브라우저 열기, 팀 조회처럼 실제 기능을 실행합니다.

“저장했다”는 문장과 실제 파일 저장은 다릅니다. 실행 가능한 도구와 그 결과를 확인해야 합니다. 모든 도구가 MCP로 제공되는 것은 아닙니다.

이번 실습: 로컬 파일 도구는 HTML을 저장하고, Vercel 도구는 배포를 요청합니다.

### MCP

AI 앱과 외부 프로그램이 기능·입력·결과를 주고받는 공통 규칙입니다.

서로 다른 서비스도 정해진 형식으로 연결할 수 있게 합니다. MCP 자체가 답을 생각하거나 웹페이지를 호스팅하지는 않습니다.

이번 실습: ChatGPT의 MCP 클라이언트 ↔ Vercel MCP 서버.

### Vercel / 배포 결과

Vercel은 전달받은 파일을 배포하고 접속할 주소를 제공합니다.

Skill로 만든 파일과 Vercel에서 열린 웹페이지는 다른 결과물입니다. URL이 생긴 뒤에도 실제 화면을 확인합니다.

이번 실습: index.html은 파일, deployment ID는 배포 1회의 식별자, Preview URL은 그 결과를 여는 주소.

- 1. 이번 요청 · 사용자 → ChatGPT: 검색어와 원하는 결과 수를 전달합니다. A는 경복궁, B는 첨성대입니다. 아직 파일이나 배포는 없습니다.
- 2. 절차 적용 · ChatGPT + Skill: heritage-brief의 지침과 API 코드를 사용해 실제 응답을 받아 검증합니다. 다른 검색어에도 같은 절차를 적용합니다. Skill이 계정이나 배포 권한을 만들어 주지는 않습니다.
- 3. 파일 생성 · 에이전트 → 파일·브라우저 도구: 에이전트가 사용 가능한 파일 도구로 index.html을 저장하고 브라우저로 확인합니다. 컴퓨터에 파일이 생겨도 아직 웹에 배포된 것은 아닙니다.
- 4. 외부 배포 · 앱의 MCP 클라이언트 ↔ Vercel MCP 서버 → Vercel: 사용자가 배포를 요청하면 Vercel MCP 도구로 파일을 전달합니다. Vercel의 결과를 받아 URL을 확인합니다. 생성·연결·인증·배포·화면 확인은 각각 확인할 일입니다.

Skill 없이 MCP 도구를 쓸 수도 있고, MCP 없이 Skill로 글이나 파일을 만들 수도 있습니다. 이번 실습에서는 두 기능을 순서대로 연결합니다.

확인 질문: 공공데이터를 조회하고 정리하는 반복 절차를 재사용하려면 무엇을 만들까요?
정답: Skill — 반복할 작업 순서와 기준은 Skill에 담습니다. 외부 서비스 기능이 필요해질 때 MCP 연결을 추가합니다.

## 2. 실행할 작업 공간 준비하기

웹 Work에서 Skill과 파일을 사용하고, 만든 결과를 계정에 남길 준비를 합니다.

실행 위치: ChatGPT 웹 → Work · 별도 실습 프로젝트

1. 기본 ZIP의 시작 안내·프롬프트·예시를 엽니다. ChatGPT 웹에서 Work를 선택하고 새 실습 프로젝트를 만듭니다.
2. Skills 페이지를 열어 Create 메뉴를 확인합니다. Create with chat은 대화로 작성, Create with editor는 직접 편집, Upload from your computer는 기존 Skill 파일 등록입니다.
3. 아래 요청으로 이 Work 작업의 Node.js/npx·Python·파일 저장 기능을 확인합니다. 웹 실행 환경과 자신의 컴퓨터는 별개입니다. Vercel 로그인은 해당 서비스 화면에서 준비합니다.

성공 확인:
- 웹의 Work와 Skills → Create 메뉴를 찾았습니다.
- 실습 프로젝트에서 파일 생성·다운로드가 가능합니다.
- 이 작업의 실행 환경과 계정 기능을 확인했습니다.

막혔을 때: 계정에 따라 메뉴가 다를 수 있습니다. 웹에 Skills/Create가 없다면 지원되는 데스크톱 또는 Codex 경로를 강사와 확인하세요. @ 글자만 입력하는 것과 등록된 Skill을 선택하는 것은 다릅니다. 예시 파일 검토는 계속할 수 있지만 실제 Skill 실행 완료로 표시하지 않습니다.

- [ChatGPT 웹 Skills 열기](https://chatgpt.com/skills)

## 3. 이미 만들어진 Skill 하나 설치하기

대표 예제 geeknews-search로 긴 절차를 재사용하는 경험을 먼저 합니다.

실행 위치: ChatGPT 웹 Work · k-skill 검토 → 등록 → Try in chat

1. k-skill의 geeknews-search 폴더에서 SKILL.md와 instruction.md를 읽습니다. 공개 RSS 조회 범위와 Node/npx·Python 의존성을 확인합니다.
2. 아래 요청을 보내 선택한 폴더만 준비합니다. 응답에 Skill 카드가 나오면 내용을 검토하고 Install을 누릅니다. ZIP만 나오면 Skills → Create → Upload from your computer에서 등록합니다.
3. Skills의 Installed 목록에서 geeknews-search를 엽니다. SKILL.md·instruction.md·scripts를 확인하고 Try in chat으로 새 대화를 시작합니다. 파일 다운로드, 계정 등록, 실제 호출은 각각 확인합니다.

성공 확인:
- 원본 작성자·사용 목적·실행 코드를 확인했습니다.
- Skills의 Installed 목록에 선택한 Skill이 보입니다.
- Try in chat을 누른 새 Work 입력창에 Skill이 선택되어 있습니다.

막혔을 때: 설치 요청에 성공했다고 답해도 Installed 목록을 확인하세요. ZIP은 선택한 Skill 폴더와 필요한 파일을 포함해야 합니다. 이미 같은 이름이 있다면 비교 없이 덮어쓰지 않습니다. 웹의 By me 표시는 내 계정에 등록한 사본이며 원본 k-skill 작성자가 바뀐다는 의미가 아닙니다.

- [k-skill · 예제 폴더 열기](https://github.com/NomaDamas/k-skill/tree/main/geeknews-search)

## 4. 뉴스를 읽고 원문과 대조하기

실제 조회 → 선택 → 원문 검토까지 수행하고, 자신의 반복 업무에 맞는 다른 Skill도 골라 봅니다.

실행 위치: ChatGPT 웹 Work · 등록한 geeknews-search의 Try in chat

1. 등록한 Skill의 Try in chat을 눌러 새 대화를 엽니다. 선택된 Skill을 유지한 채 아래 요청을 추가합니다. 최신 글 5개와 읽을 만한 2개, 선택 이유를 확인합니다.
2. 반환된 제목에서 키워드 하나를 골라 같은 Skill에 검색을 요청합니다. 원문 링크 하나를 직접 열어 제목과 요약을 대조합니다.
3. 관심 글 두 개를 골라 “읽을 이유 / 확인할 질문”을 적습니다. 응용하려면 k-skill 목록에서 본인 업무에 맞는 Skill 하나를 골라 입력·로그인 필요 여부·성공 기준을 비교합니다.

성공 확인:
- 실제 feed 조회 결과와 출처 링크가 있습니다.
- 선택한 글의 원문을 열어 요약의 범위를 확인했습니다.
- 다른 Skill에도 적용할 입력과 성공 기준을 말할 수 있습니다.

막혔을 때: 검색 범위는 현재 RSS/Atom 피드입니다. 결과가 0개여도 전체 GeekNews에 글이 없다는 뜻은 아닙니다. 요약에 없는 전문·댓글·추천 수를 읽었다고 단정하지 않습니다. 결과의 제목과 건수는 실행 시점마다 바뀝니다.

## 5. Skill 파일의 각 부분 이해하기

이름·설명·본문과 선택적인 보조 파일의 역할을 읽습니다.

실행 위치: 이 페이지 · Skill 구성요소 탐색

1. SKILL.md, name, description, 본문을 차례대로 눌러 역할을 읽습니다.
2. scripts·references·assets는 어떤 경우에 추가하는지 비교합니다. 이번에는 API 호출 코드와 참고자료를 만듭니다.
3. skill-creator와 우리가 만들 heritage-brief가 어떻게 다른지 확인합니다.

성공 확인:
- name, description, 본문의 차이를 말할 수 있습니다.
- SKILL.md와 호출 코드·API 참고자료의 역할을 구분합니다.
- 입력 예시와 Skill, 생성 파일을 구분할 수 있습니다.

막혔을 때: 파일 구조를 모두 외우지 않아도 됩니다. 먼저 이름·적용 상황·작업 절차 세 가지를 읽고, 보조 폴더는 필요할 때 확인하세요.

### Skill은 “언제 쓰고, 어떻게 수행할지”를 담은 재사용 가능한 작업 묶음입니다.

이번에는 공식 API에서 문화유산 정보를 가져오는 heritage-brief를 만듭니다. 최소 구성은 SKILL.md이고, 반복 호출 코드는 scripts, 상세 API 계약은 references로 분리합니다.

매뉴얼의 이름표(name), 적용 대상(description), 작업 순서(본문)를 나눠 생각하면 쉽습니다. 설명을 자세히 적어도 없는 도구·계정 권한이 자동으로 생기지는 않습니다.

### SKILL.md · 필수

Skill의 안내 정보와 실제 지침이 들어가는 중심 파일입니다.

Markdown은 제목·목록을 쓰는 텍스트 형식입니다. 맨 위 --- 사이의 YAML 머리말에는 이름·설명 같은 메타데이터를 적고, 그 아래에 작업 지침을 씁니다.

예시:

---
name: heritage-brief
description: 문화유산명으로 공식 정보를 조회할 때 사용
---

1. 검색어를 확인한다.
2. 호출 스크립트를 실행한다.
3. 응답·출처·오류를 검증한다.

이번 실습: 이번에는 SKILL.md와 호출 코드, API 참고자료를 함께 만듭니다.

### name · 이름

어떤 Skill인지 구별하고 이름으로 선택할 때 사용합니다.

이름만으로 기능이 구현되는 것은 아닙니다. 실제 기능은 아래 지침과 실행 가능한 도구에 달려 있습니다.

예시:

name: heritage-brief

이번 실습: @ 선택기에서 heritage-brief를 고릅니다.

### description · 적용 상황

어떤 요청에 이 Skill을 쓸지 판단하는 단서입니다.

무엇을 하는지, 언제 쓰는지, 어디까지 다루는지 적습니다. 홍보 문장보다 작업 범위가 중요합니다.

예시:

description: Fetch official Korean heritage facts for a name search.

이번 실습: 문화유산명 검색·공식 정보 요약에는 사용. 운영시간 추정·예약·배포는 제외.

### 본문 · 작업 순서와 기준

입력 읽기부터 결과 확인까지 실행할 절차를 설명합니다.

작업 순서뿐 아니라 결과 형식과 성공·실패 구분도 필요합니다. “정보 찾기”보다 “실제 응답과 출처를 JSON으로 저장”이 검토하기 쉽습니다.

예시:

## Procedure
- Read the search keyword.
- Run the API helper.
- Check status and source URLs.
- Keep missing facts unknown.
- Keep deployment separate.

이번 실습: 입력 → 목록 → 상세 → JSON → 출처·조회 시각 확인.

### scripts/ · 선택

반복 실행할 코드를 함께 둘 수 있습니다.

예를 들어 파일 형식을 검사하는 Python 코드를 둘 수 있습니다. 파일이 있다는 것과 코드가 실행됐다는 것은 다릅니다. 실행 도구와 환경이 필요합니다.

이번 실습: scripts/heritage_query.py: HTTP 요청·XML 파싱·JSON 출력·오류 처리를 반복 실행합니다.

### references/ · 선택

필요할 때 읽을 상세 자료를 둡니다.

긴 규칙이나 제품 용어집을 별도 파일로 분리할 수 있습니다. 본문에서 언제 어떤 자료를 읽을지 알려 줍니다.

이번 실습: references/api.md: 공식 주소, 파라미터, 응답 필드, 제한 사항을 필요할 때 읽습니다.

### assets/ · 선택

결과물을 만들 때 쓸 템플릿이나 이미지 등을 둡니다.

읽는 설명 자료와 출력에 활용할 재료를 구분합니다. 로고나 HTML 틀 같은 파일이 해당합니다.

이번 실습: 예: 승인된 로고, 페이지 템플릿. 이번 실습에는 없습니다.

### agents/openai.yaml · 선택

앱에서 보이는 이름·설명이나 도구 의존성 같은 추가 설정을 담을 수 있습니다.

최소 Skill에 필수인 파일은 아닙니다. 앱별 설정이며, 작성한다고 계정 인증이 완료되는 것도 아닙니다.

이번 실습: 이번에는 SKILL.md의 적용 상황과 scripts·references 연결부터 이해하면 됩니다.

- 1. 찾기 · name + description: 어떤 Skill을 쓸지 이름과 적용 상황을 확인합니다. 이번에는 @로 직접 선택합니다. 설명은 선택의 단서입니다.
- 2. 읽기 · SKILL.md 본문: 선택한 Skill의 전체 작업 지침을 읽고 이번 요청에 적용합니다. 본문은 작업 순서와 확인 기준입니다.
- 3. 필요할 때 더 보기 · 보조 자료·코드: 지침에서 필요로 하는 참고 자료나 보조 코드를 사용합니다. 항상 모든 파일을 한꺼번에 읽는 것은 아닙니다. 이번 예시는 API 계약을 읽고 Python 호출 코드를 실행합니다.

skill-creator는 Skill을 만드는 도우미, heritage-brief는 새로 만들 절차, 검색어 A/B는 입력, JSON은 실제 실행 결과입니다. k-skill은 남이 만들어 둔 Skill 모음으로 별도 실습입니다.

확인 질문: description과 본문은 무엇이 다른가요?
정답: description은 적용 상황, 본문은 수행 절차 — 언제 이 Skill이 적절한지와, 선택한 뒤 어떻게 일할지를 구분하면 다른 입력에도 재사용하기 좋습니다.

## 6. 어떤 API를 호출하는지 먼저 읽기

공공데이터포털은 데이터 안내, 제공기관의 API는 실제 데이터를 주는 창구입니다.

실행 위치: 공공데이터포털 → 국가유산청 공식 Open API

1. 데이터 설명 링크에서 “국가유산청_전국 지정문화재 현황”을 확인하고 제공기관 안내로 이동합니다. 이번 API는 별도 인증키 없이 조회됩니다. 모든 공공데이터 API가 그런 것은 아닙니다.
2. 목록 API의 검색어·페이지·결과 수를 읽습니다. 반환되는 XML에서 totalCnt와 item, 상세 조회에 쓸 세 식별자를 찾습니다.
3. 상세 API에 목록에서 받은 식별자를 전달합니다. 이름·주소·설명은 응답에서 얻고, 운영시간·입장료는 추측하지 않습니다.

성공 확인:
- 포털 설명 페이지와 실제 API 주소를 구분합니다.
- 전체 결과 수와 이번에 받은 결과 수가 다름을 이해합니다.
- 상세 조회의 식별자는 응답에서 가져옵니다.

막혔을 때: 제공기관은 브라우저 클라이언트 직접 호출을 지원하지 않는다고 안내합니다. 이 실습은 에이전트의 Python 환경에서 호출합니다. 웹페이지에는 조회한 스냅샷을 넣습니다. 통신 오류를 “검색 결과 없음”으로 바꾸지 않습니다.

### Endpoint · 주소

어느 기능에 요청할지 정합니다. 목록과 상세는 다른 주소입니다.

SearchKindOpenapiList.do → 목록 / SearchKindOpenapiDt.do → 상세

### Parameters · 입력

검색 조건과 받을 범위를 지정합니다.

ccbaMnm1=경복궁, pageUnit=3, pageIndex=1

### XML → JSON

XML은 기관의 응답 형식, JSON은 이번 Skill에서 정리해 저장할 형식입니다.

totalCnt=11, 이번 item 3개 → total: 11, returned: 3

### Detail IDs · 상세 식별자

목록에서 받은 세 값을 그대로 함께 사용합니다. 숫자로 바꾸면 앞의 0이 사라질 수 있습니다.

ccbaKdcd + ccbaAsno + ccbaCtcd → 모두 문자열

### API key · 인증키

서비스에 따라 접근 권한을 확인하는 값입니다. 이번 API에는 필요하지 않습니다.

다른 API에 키가 필요하면 해당 서비스의 보호된 설정에서 관리; 프롬프트·브라우저 코드에 넣지 않기

- [공공데이터 설명](https://www.data.go.kr/data/15034324/openapi.do)
- [목록 API 예시 열기](https://www.khs.go.kr/cha/SearchKindOpenapiList.do?ccbaMnm1=%EA%B2%BD%EB%B3%B5%EA%B6%81&pageUnit=3&pageIndex=1)

실행 위치: 등록한 heritage-brief → Try in chat

1. 새 Skill을 선택하고 입력 A를 전달합니다. 실제 호출 내역과 생성된 heritage-a.json을 엽니다.
2. 전체 일치 수(totalCnt/totalCount), 이번 수집 수, 상세 성공 수, 조회 시각을 읽습니다. 파일마다 키 이름이 다르면 생성한 스키마와 대조하세요. 최대 3개는 전체 건수나 성공 보장이 아닙니다.
3. 항목 하나의 공식 출처를 열고 이름·주소를 비교합니다. 요약이 원래 설명에 없는 내용을 추가하지 않았는지 확인합니다.

성공 확인:
- 실제 호출 내역과 결과 JSON이 있고 오류 여부를 구분했습니다.
- 정상 결과는 목록 식별자와 상세의 대응을 확인했습니다. 실패라면 다음 복구 단계에서 원인을 분리합니다.
- 출처·시각·누락 상태가 있고 없는 사실을 만들지 않았습니다.

막혔을 때: 검수 시 Chrome에서는 전체 11건 중 3건을 받았지만 웹 에이전트의 같은 요청은 502였습니다. 오류 상태와 조회 환경을 남깁니다. 아래 공식 요청을 브라우저에서 직접 열어 XML을 저장·첨부하는 복구 경로를 쓸 수 있습니다. 이때 sourceMode=provided_snapshot, 원래 조회 시각, 상세 응답 누락을 표시하며 실시간 호출 성공으로 세지 않습니다.

## 9. 입력을 바꾸고 실패도 확인하기

재사용이란 이전 답을 복사하는 것이 아니라 같은 절차를 새 입력에 적용하는 것입니다.

실행 위치: ChatGPT Work · 새 작업 + 같은 @heritage-brief

1. 입력 B를 전달해 heritage-b.json을 만듭니다. A는 보존합니다. 반환된 이름이 새 검색어에 맞는지 확인합니다.
2. 존재하지않는유산zzzz로 한 번 더 호출합니다. 정상적인 0건 응답과 통신 실패를 서로 다르게 보고하는지 봅니다.
3. 실제 호출이 계속 실패하면 정상·0건·통신 오류를 모의한 검사를 별도로 요청합니다. 모의 검사를 실제 API 성공이라고 표시하지 말고, 파싱 검사는 브라우저에서 저장한 실제 XML과도 대조합니다.

- B의 검색어로 새 호출을 했고 실제 상태·응답을 기록했습니다.
- A의 파일이 보존됐습니다.
- 0건과 조회 실패를 다른 상태로 처리합니다.

막혔을 때: 이전 로컬 검수에서 첨성대는 1건이었지만, 이번 웹 실행 환경에서는 502였습니다. 두 환경을 같은 성공 기록으로 합치지 않습니다. 최대 3개라고 해서 3개를 지어내면 안 됩니다.

## 10. 실제 XML을 첨부해 원인을 분리하기

통신 실패와 파싱·표시 문제를 나누어 확인합니다. 실시간 성공을 가장하지 않습니다.

실행 위치: 브라우저에서 공식 XML 저장 → Skill Creator로 첨부 처리 경로 추가

1. 같은 공식 목록 요청을 브라우저에서 열어 봅니다. 정상 XML이 보이면 파일로 저장하세요. API 전체 장애와 특정 실행 환경의 연결 실패는 다릅니다.
2. 목록의 식별자로 상세 요청 하나도 저장하세요. 아래 검수용 XML ZIP에는 실제 목록 3건과 근정전 상세 1건만 있습니다.
3. 두 XML을 첨부하고 아래 요청을 보냅니다. 전체 11건·수집 3건·상세 1건·누락 2건을 구분하고 원래 수집 시점을 기록합니다.
4. 새 Skill 버전을 저장하고 같은 첨부로 다시 실행합니다. 상세가 없는 2건의 주소·설명을 만들지 않는지 JSON에서 확인하세요.

성공 확인:
- sourceMode가 provided_snapshot이고 원래 조회 시점이 있습니다.
- 부분 결과는 partial이며 누락 상세는 missing으로 구분됩니다.
- 실제 첨부 파싱·모의 검사·실시간 API 호출의 결과를 따로 기록했습니다.

막혔을 때: 이 단계는 선택 복구 경로입니다. API 호출이 정상이라면 본인 결과를 그대로 사용합니다. 첨부 XML도 구할 수 없으면 아래 검수 시점 파일로 파싱만 연습하고 현재 데이터 조회를 완료했다고 표시하지 않습니다.

## 11. 검증한 데이터를 작은 웹페이지로

1. 검토한 결과 JSON을 첨부합니다. 정상 결과가 하나뿐이면 하나로 시작하고, A/B 두 결과가 모두 검증됐을 때만 전환을 추가합니다.
2. 생성된 HTML을 직접 엽니다. 검색·설명 펼치기·공식 출처·조회 시점과 누락 정보를 확인합니다.
3. 아래 실제 웹 실습 결과는 경복궁 목록 3건·상세 1건의 첨부 스냅샷입니다. 디자인을 복제하는 것이 아니라 표시가 데이터와 일치하는지 확인합니다.

성공 확인:
- 내 결과 파일을 쓰는 index.html이 있습니다.
- 조회 시각과 스냅샷이라는 표시가 보입니다.
- 사용자가 데이터를 바꾸어 보고 출처를 열 수 있습니다.

막혔을 때: 브라우저에서 공공 API를 직접 호출하려다가 CORS로 막히는 흐름을 피합니다. 이번 결과는 스냅샷입니다. 실시간 서비스는 서버 호출·캐시·인증 관리가 추가로 필요한 확장 과제입니다.

## 12. 클릭해서 동작을 증명하기

스크린샷만으로는 검색이나 버튼이 제대로 작동하는지 알 수 없습니다.

실행 위치: 실제 생성한 index.html · 브라우저

1. 경회루 검색 → 1건 확인 → 초기화 → 3건 복원을 확인합니다. 정상 A/B 결과를 모두 가진 경우에만 전환 후 이전 결과가 남지 않는지도 검사합니다.

성공 확인:
- 검색·초기화·0건 안내를 직접 사용했습니다. A/B를 구현했다면 전환도 확인했습니다.
- 설명·출처를 확인하고 작은 화면에서도 조작했습니다.
- 수정했다면 같은 조작을 다시 확인했습니다.

막혔을 때: 에이전트에 브라우저 도구가 없어도 학습자가 직접 검사할 수 있습니다. “테스트 통과”만 적지 말고 어떤 버튼을 눌렀고 결과가 어땠는지 남깁니다.

## 13. MCP는 어떻게 도구를 연결하나요?

앱·클라이언트·서버·도구와 인증의 역할을 구분합니다.

실행 위치: 이 페이지 · 연결 구조와 요청/응답 흐름

1. Host부터 OAuth까지 눌러 구성요소별 역할을 읽습니다.
2. 요청 흐름을 넘기며 팀 목록이 모델의 추측이 아니라 도구 결과에서 오는지 확인합니다.
3. 연결과 실제 실행의 차이를 확인한 뒤 다음 단계에서 설정합니다.

성공 확인:
- Host·Client·Server·Tool의 역할을 구분합니다.
- 서버 주소, 통신 방식, 계정 인증의 의미를 이해했습니다.
- 연결됨과 도구 실행 성공을 구분할 수 있습니다.

막혔을 때: Host는 앱, Client는 그 앱의 연결 담당, Server는 기능 제공 프로그램이라고 먼저 기억하세요. 이번에는 MCP 서버를 직접 개발하는 것이 아니라 Vercel 서버에 연결합니다.

### MCP는 Model Context Protocol — AI 앱과 외부 기능을 연결하는 표준입니다.

“내 Vercel 팀을 조회해 줘”라는 말만으로 모델이 계정 정보를 알 수는 없습니다. 앱이 연결된 MCP 서버의 도구를 찾고, 필요한 입력을 보내고, 실제 결과를 받아야 합니다.

MCP는 직원과 외부 서비스가 주고받는 주문서·응답서의 공통 규격에 가깝습니다. 주소는 어디로 연결할지, 인증은 누구의 권한으로 사용할지, 도구 입력은 무엇을 할지 정합니다.

### Host · AI 앱

사용자 요청·모델·도구 연결을 함께 관리하는 앱입니다.

이번 실습의 호스트는 ChatGPT 앱입니다. Settings와 도구 실행 확인 화면도 이 앱에서 봅니다. 모델 자체와 앱은 구분합니다.

이번 실습: ChatGPT Work에서 “팀을 조회해 줘”라고 요청합니다.

### Client · 앱 안의 연결 담당

호스트 안에서 특정 MCP 서버와 요청·응답을 주고받습니다.

일반 학습자가 별도 클라이언트 프로그램을 작성할 필요는 없습니다. 앱이 서버별 연결을 관리합니다.

이번 실습: ChatGPT 안의 Vercel 연결 담당이 도구 요청을 전달합니다.

### Server · 기능 제공 프로그램

사용 가능한 도구의 설명과 입력 형식을 내보내고 호출을 처리합니다.

MCP 서버는 서버 컴퓨터 자체가 아니라 프로그램을 뜻합니다. 내 컴퓨터에서 실행될 수도 있고 서비스 업체가 원격으로 제공할 수도 있습니다.

이번 실습: 이번에는 Vercel이 제공하는 원격 MCP 서버에 연결합니다.

### Tool · 실행할 기능

서버가 공개한 작업 하나입니다. 이름·설명·입력 형식을 보고 호출합니다.

조회와 변경은 다른 도구입니다. “배포해 줘”라고 말해도 해당 도구가 연결·허용되어 있지 않으면 수행할 수 없습니다.

이번 실습: list_teams는 팀 조회, deploy_to_vercel은 파일 배포 요청입니다.

### Arguments / Result · 입력과 결과

도구에 전달할 구체적인 값과 실행 뒤 돌려받은 정보입니다.

입력 스키마는 필수 항목과 값의 형식을 정한 양식입니다. 결과에는 데이터뿐 아니라 실패 정보도 올 수 있습니다.

이번 실습: 배포 입력: 팀·프로젝트·파일·target. 결과 확인: 실제 배포 ID·상태·URL.

### Resources · 참고 데이터

서버가 읽을 수 있도록 제공하는 자료입니다.

실행을 요청하는 Tool과 달리, 앱이 작업에 참고할 내용을 가져오는 용도입니다. 제공 여부와 읽는 방식은 서버와 앱의 지원에 따라 다릅니다.

이번 실습: 일반적인 예: 문서 내용이나 데이터베이스 구조. 이번 Vercel 실습에서는 Tools를 사용하며 Resources가 있다고 가정하지 않습니다.

### Prompts · 서버의 요청 틀

서버가 제공하는 재사용 가능한 요청문 템플릿입니다.

사용자가 매번 직접 쓰는 일반 프롬프트와 달리 서버에서 제공하는 기능입니다. Skill처럼 폴더와 절차를 묶은 패키지와도 구분합니다.

이번 실습: 일반적인 예: 프로젝트 정보를 넣어 분석 요청을 만드는 틀. 이번 실습에서 복사하는 요청문은 이 사이트가 제공하는 일반 프롬프트입니다.

### Transport · 전달 방식

요청과 결과가 이동하는 통신 방식입니다.

Streamable HTTP는 HTTP를 사용하는 연결 방식입니다. STDIO는 내 컴퓨터에서 실행한 프로그램의 입력·출력으로 통신합니다.

이번 실습: Vercel 실습은 원격 주소에 연결하므로 Streamable HTTP를 고릅니다.

### OAuth · 계정 접근 허용

Vercel 로그인 화면에서 접근할 계정과 허용 범위를 확인합니다.

서버 주소를 입력한 것은 인증 완료가 아닙니다. 계정 연결, 개별 작업의 실행 확인, 실제 실행 성공도 서로 다릅니다.

이번 실습: Authenticate → Vercel 로그인·허용 → 앱으로 복귀 → 조회 도구 실행.

- 1. 기능 찾기 · 앱의 Client ↔ MCP Server: 앱이 사용할 수 있는 도구와 필요한 입력을 확인합니다. 없는 기능을 만들어 냈다고 가정하지 않습니다. 도구 이름·설명·입력 형식을 알게 됩니다.
- 2. 요청 구성 · 사용자 요청 → 도구 선택: 에이전트가 “팀 조회”에 맞는 list_teams를 고릅니다. 배포라면 별도로 팀·파일 등 입력이 필요합니다. 일반 답변과 도구 호출은 다릅니다.
- 3. 실제 실행 · Client → Server → Vercel: 앱이 연결과 권한을 확인해 요청을 보내면 서버가 Vercel 기능을 사용합니다. 필요한 확인 절차는 앱에서 진행합니다. 연결됨 표시만으로 이 단계가 성공한 것은 아닙니다.
- 4. 결과 읽기 · Vercel → Server → Client → 답변: 돌아온 팀 목록이나 오류를 읽고 다음 행동을 정합니다. 배포 후에는 상태와 실제 URL의 화면도 따로 봅니다. 결과를 근거로 말하는지 호출 내역을 펼쳐 확인합니다.

MCP 서버가 제공할 수 있는 것은 Tools(실행 기능), Resources(참고 데이터), Prompts(요청 템플릿)입니다. 모든 서버가 세 가지를 모두 제공하지는 않습니다. 이번 Vercel 실습의 중심은 Tools입니다. 서버의 Prompts와 우리가 복사하는 일반 요청문, Skill 패키지도 같은 것은 아닙니다.

확인 질문: MCP에 연결됨이라고 표시되면 이미 웹페이지가 배포된 건가요?
정답: 아니요. 배포 도구 호출과 결과 확인이 따로 필요해요 — 연결은 통로를 준비한 상태입니다. 실제 파일과 대상이 들어간 배포 요청, 성공 상태, URL 확인이 이어져야 합니다.

## 14. 웹에서 Vercel 도구 연결하기

외부 서비스 도구를 연결하고, 어느 계정의 권한으로 사용하는지 확인합니다.

실행 위치: ChatGPT 웹 Plugins → Vercel → Install plugin

1. 아래 Plugins 링크에서 Vercel을 검색하고 개발자가 Vercel Labs인지 확인합니다. Install plugin을 선택합니다. 웹에서는 데스크톱의 MCP servers 메뉴를 찾지 않습니다.
2. 기존 Vercel 계정으로 로그인하고 필요한 연결을 진행합니다. 이메일 인증이 나오면 서비스 화면에서 직접 완료합니다. 계정·권한 범위를 확인하며 실습과 관계없는 범위는 추가하지 않습니다.
3. 페이지를 만든 Work 작업에서 Vercel을 선택합니다. 연결 표시와 실제 도구 조회를 다음 단계에서 따로 확인합니다. Plugin은 Skill과 앱 연결을 묶을 수 있으며 MCP는 도구를 주고받는 규칙입니다.

성공 확인:
- 웹에서 공식 Vercel 플러그인을 찾았습니다.
- 서비스 화면의 로그인·인증·계정 연결을 완료했습니다.
- Work에서 Vercel 도구를 선택할 수 있습니다.

막혔을 때: Install, 이메일 로그인, 서비스 권한 연결은 서로 다른 단계입니다. 인증창이 남아 있으면 연결 완료가 아닙니다. 새 계정을 만들 필요가 없다면 기존 계정을 사용하세요. 웹 플러그인과 데스크톱 수동 MCP 설정을 섞지 마세요. 인증코드·비밀번호는 요청문에 넣지 않습니다.

- [ChatGPT Plugins에서 Vercel 찾기](https://chatgpt.com/plugins?q=Vercel)

## 15. 첫 도구 호출은 조회부터

연결됨 표시뿐 아니라 실제 도구가 실행되는지 확인합니다.

실행 위치: ChatGPT 웹 Work · 연결한 Vercel 도구

1. 아래 요청문으로 정적 페이지 배포 문서와 접근 가능한 팀을 조회합니다.
2. 도구 호출 내역과 반환 결과를 펼칩니다. 현재 연결이 제공하는 배포 도구의 실제 이름과 파일 입력 지원을 확인합니다. 도구 이름이 문서와 다르면 현재 도구 스키마를 따릅니다.
3. 배포할 팀의 이름과 ID를 확인하고, 기존 프로젝트와 겹치지 않는 새 실습 프로젝트 이름을 정합니다. 다음 단계의 두 칸에 사용합니다.

성공 확인:
- Vercel 조회 도구가 실행된 기록이 있습니다.
- 배포할 팀의 이름과 ID를 확인했습니다.
- 직접 파일 배포 도구의 사용 가능 여부를 확인했습니다.

막혔을 때: 일반 답변만 나오고 도구 호출이 없으면 MCP를 다시 확인합니다. 배포 도구가 없으면 생성 파일을 보존하고 사용 가능한 도구 목록과 오류를 강사에게 보여 주세요. 배포했다고 가정하고 다음 단계로 넘어가지 않습니다.

## 16. Preview 주소 만들기

검토한 문화유산 페이지 파일을 지정한 팀의 새 실습 프로젝트로 배포합니다.

실행 위치: ChatGPT Work · 문화유산 페이지 작업에서 Vercel MCP 실행

1. 아래에 조회 결과의 팀 ID 또는 slug와 사용할 새 프로젝트 이름을 입력합니다. 비밀번호나 토큰을 넣는 칸이 아닙니다.
2. 완성된 요청문을 복사해 보냅니다. 실행할 파일 목록·팀·프로젝트·preview 대상을 검토하고, 앱이 요청하는 도구 실행 확인을 진행합니다.
3. 반환된 실제 deployment ID와 URL을 보관합니다. 파일 경로나 예시 URL을 배포 URL과 혼동하지 않습니다.

성공 확인:
- 대상이 지정한 실습 팀과 프로젝트입니다.
- 실제 deployment ID와 Preview URL을 받았습니다.
- 빌드가 진행 중이면 다음 단계에서 최종 상태를 확인합니다.

막혔을 때: 이 경로는 파일을 직접 전달하므로 Git 저장소나 CLI가 먼저 필요하지 않습니다. 도구가 사용할 수 없거나 빌드가 실패하면 실제 오류를 확인합니다. 다른 배포 서비스나 기존 프로젝트로 임의 전환하지 마세요.

## 17. 실제 URL에서 확인하기

빌드 성공, 페이지 열림, 기능 동작을 각각 확인합니다.

실행 위치: ChatGPT + 브라우저의 새 Preview URL

1. 아래 요청문으로 방금 생성한 배포의 상태를 확인합니다. 오류가 있으면 해당 배포 ID의 빌드 로그부터 읽습니다.
2. 반환된 URL을 브라우저에서 직접 엽니다. Vercel 로그인을 요구하면 Preview 보호 여부와 자신의 접근 권한을 확인합니다.
3. 제목·A/B 전환·검색·설명·좁은 화면을 다시 확인합니다. URL이 생긴 것만으로 모든 동작이 검증된 것은 아닙니다.

성공 확인:
- 배포 상태가 성공으로 확인됩니다.
- 의도한 접근 환경에서 URL이 열립니다.
- 배포된 화면에서 검색과 설명 펼치기를 직접 사용했습니다.

막혔을 때: 로컬 파일은 정상인데 배포 화면이 다르면 최신 배포 ID, 파일 경로, 실제 포함된 파일을 확인하세요. Preview와 production은 모두 접근 제한이 있을 수 있습니다. 보호를 자동으로 끄지 않습니다.

## 18. 한 가지만 바꾸고 재배포하기

작은 변경 → 차이 검토 → 새 URL 확인까지 연결합니다.

실행 위치: ChatGPT Work · 같은 문화유산 페이지 작업과 실습 프로젝트

1. 이전 배포 ID와 URL을 남겨 둡니다. 아래 프롬프트로 제목 하나만 바꾸도록 요청합니다.
2. 수정 전후 차이를 읽고 다른 내용이 바뀌지 않았는지 확인한 다음, 같은 프로젝트의 새 Preview로 배포합니다.
3. 새 URL에서 우리 동네 유산, 근거와 함께.가 보이는지 확인합니다. A/B 전환과 검색도 다시 사용하고 완료로 표시합니다.

성공 확인:
- 제목이 우리 동네 유산, 근거와 함께.로 바뀌었습니다.
- 동일 프로젝트에 새 배포 ID와 URL이 있습니다.
- 새 URL에서도 A/B 전환과 검색가 동작합니다.

막혔을 때: 제목이 그대로라면 이전 URL을 보고 있는지 확인하세요. 불필요한 변경이 섞였으면 해당 부분만 되돌리도록 요청하고, 이전 정상 배포 기록을 보존합니다.

## 19. 다른 사람이 다시 써 볼 수 있나요?

Skill·데이터·배포의 역할을 설명하고, 재사용 가능한 결과를 남깁니다.

실행 위치: 완성 Skill + API 결과 + 검증한 페이지

1. 짝에게 검색어 하나를 새로 받습니다. 같은 Skill을 실행해 출처와 오류 처리까지 설명합니다.
2. k-skill을 쓴 부분과 직접 만든 Skill을 구분하고, MCP가 어느 단계에 필요했는지 말합니다.
3. API Skill 본문, 실제 응답 하나, 확인 기록과 페이지 URL을 정리합니다. 배포가 막혔다면 로컬 화면까지 확인한 범위와 남은 오류를 정확히 남깁니다.

성공 확인:
- 자기 입력으로 재사용할 수 있습니다.
- 실제 확인한 것과 아직 확인하지 못한 것을 구분합니다.
- 다음 업무에 적용할 입력·출력·성공 기준을 정했습니다.

막혔을 때: 계정 설정에 막혀도 이미 만든 Skill·API 결과·페이지는 보존합니다. 연결 문제를 콘텐츠 문제와 분리하여 해결한 뒤 같은 파일을 배포하면 됩니다.

## 선택 경로: 데스크톱 수동 MCP 설정값

웹의 Vercel 플러그인 설치와 별개인 경로입니다.

### Name · 연결 이름

앱 안에서 이 연결을 구별할 별명입니다.

vercel이라는 이름만 입력해서 연결되는 것은 아닙니다. 실제 연결 대상은 URL로 정합니다.

이번 실습: 여러 MCP를 연결했다면 이름으로 어느 서비스를 쓰는지 구분합니다.

### Type · 통신 방식

앱과 서버가 요청·응답을 전달할 방법입니다.

Streamable HTTP를 고르는 이유는 Vercel이 원격 HTTP 주소를 제공하기 때문입니다. 내 컴퓨터의 프로그램을 실행하는 STDIO와 다릅니다.

이번 실습: 이번 실습에서는 Streamable HTTP를 선택합니다.

### URL · MCP 서버 주소

앱이 도구 목록과 실행 요청을 보낼 주소입니다.

이 주소는 우리가 만들 웹페이지 주소가 아닙니다. 서버를 연결해도 아직 페이지를 배포한 것이 아닙니다.

이번 실습: https://mcp.vercel.com은 도구 연결 주소입니다.

### Authenticate · 계정 허용

어느 계정의 어떤 권한으로 기능을 사용할지 확인합니다.

Vercel 로그인 화면에서 계정과 접근 범위를 확인합니다. 로그인은 개별 배포 완료와는 별개입니다.

이번 실습: 인증 후 팀 조회 도구를 실행해 실제 접근 가능한 팀을 확인합니다.

### /mcp · 연결 상태

앱에서 설정된 MCP 연결 상태를 확인하는 명령입니다.

연결 상태는 통로의 상태입니다. 실제 조회 결과나 배포 상태는 해당 도구 실행으로 확인합니다.

이번 실습: 연결됨 → 팀 조회 성공 → 배포 성공을 따로 확인합니다.

## 배포 입력값

### teamId · 소유 팀

누구의 작업 공간에 배포할지 정합니다.

ID는 팀을 구별하는 값이고, slug는 주소 등에 쓰는 짧은 이름입니다. 임의의 예시 값이 아니라 조회된 값을 씁니다.

이번 실습: 팀 조회 결과를 아래 팀 ID 또는 slug 칸에 입력합니다.

### name · 프로젝트

하나의 사이트를 관리하는 묶음의 이름입니다.

프로젝트 하나에 여러 배포 버전이 생길 수 있습니다. 처음에는 새 이름을 쓰고 수정 배포는 같은 프로젝트에 합니다.

이번 실습: 같은 프로젝트 → 처음 만든 배포 → 제목을 바꾼 새 배포.

### files · 실제 파일

배포할 파일의 경로와 전체 내용을 전달합니다.

파일 이름이나 내 컴퓨터 경로만 알려 주는 것으로는 부족합니다. file은 상대 경로, data는 내용, encoding은 내용을 표현한 방식입니다.

이번 실습: index.html: HTML은 내용·구조, CSS는 모양, JavaScript는 필요한 동작을 담당합니다. 이번 페이지는 CSS를 HTML 안에 넣습니다.

### target · 배포 용도

preview는 검토용, production은 정식 서비스용으로 구분합니다.

Preview도 실제 서버에 올라간 결과입니다. 검토용이라고 반드시 본인만 볼 수 있거나, production이라고 반드시 누구나 볼 수 있는 것은 아닙니다.

이번 실습: 이번 필수 실습은 preview입니다. 접근 가능 여부는 URL에서 따로 확인합니다.

### ID · 상태 · URL

배포 1회를 구분하고 결과를 확인하는 정보입니다.

deployment ID는 배포 식별자, 상태는 진행·성공·실패 여부, URL은 결과를 열 주소입니다. 프로젝트 이름과 배포 ID는 다릅니다.

이번 실습: 상태 성공 → URL 열기 → 제목·링크·FAQ 동작 확인. 수정 후에는 새 배포 결과를 봅니다.
