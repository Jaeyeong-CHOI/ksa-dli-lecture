# Skill → MCP → Vercel

반복 작업을 Skill로 만들고, 결과 페이지를 Vercel MCP로 배포하는 실습입니다.

## 준비

- 기본 화면: **ChatGPT 데스크톱 앱의 Work**. 새 작업에서 사용할 폴더를 선택합니다.
- Skills 메뉴와 `@skill-creator`가 보이는지 확인합니다.
- Vercel 계정과 실습용 팀/워크스페이스를 준비합니다.
- 데스크톱의 Settings → MCP servers → Add server가 보이는지 확인합니다.
- 실습에는 공개해도 되는 가상 예시만 사용합니다. 인증은 Vercel 로그인 창에서 진행하며 토큰을 채팅에 붙여넣지 않습니다.

웹 브라우저 ChatGPT는 플러그인으로 제공되는 Skill/원격 도구를 사용하는 경로입니다. 로컬 Skill 폴더나 데스크톱 MCP 설정이 웹에 자동 반영되지 않습니다. 메뉴가 다르면 먼저 수업의 데스크톱 경로로 맞춥니다. 관리형 계정은 기능 허용 여부도 확인합니다.

## 파일 3개만 사용합니다

- `READ_ME.md`: 시작 순서와 막혔을 때 확인할 곳
- `PROMPTS.md`: 번호 순서대로 복사하는 요청문
- `EXAMPLES.md`: Skill 본문 예시 + 서로 다른 입력 A/B

텍스트 편집기에서 파일을 열거나, ChatGPT에 첨부한 뒤 필요한 예시와 요청문을 사용합니다.

## 개념부터 이해하기

웹 실습은 개념 3단계와 실행 10단계, 총 13단계입니다. 아래 개념을 읽고 따라하기로 이어 가세요. PROMPTS.md의 번호는 PPT와 함께 쓰는 요청문 번호이며 웹 단계 번호와 다릅니다.

## Skill은 작업 설명서, MCP는 외부 도구와 대화하는 규칙입니다.

“이 소개 글로 웹페이지를 만들고 주소를 알려 줘.” 한 문장이지만, 내용을 이해하기·파일 만들기·외부에 배포하기는 서로 다른 일입니다. 에이전트는 이 일을 나누고, 사용할 절차와 도구를 골라 결과를 확인합니다.

직원에게 업무를 맡긴다고 생각해 보세요. 프롬프트는 이번 주문, Skill은 반복 업무 매뉴얼, 도구는 실제 업무 기능입니다. MCP는 다른 시스템의 기능을 찾아 요청하고 결과를 받기 위한 공통 약속에 가깝습니다.

### 프롬프트

이번에 원하는 결과와 재료를 전달합니다.

매번 달라지는 요구사항을 담습니다. Skill이 있어도 이번 작업의 입력은 필요합니다.

이번 실습: 입력 A: AI Study Club 소개 페이지를 만들어 줘.

### LLM / 에이전트

요청을 이해하고 다음 행동을 고릅니다.

LLM은 글과 코드를 생성합니다. 에이전트는 앱 안에서 도구의 실행 결과를 보고 다음 작업도 이어 갑니다. 모델이 직접 인터넷 서버가 되는 것은 아닙니다.

이번 실습: 소개 글 정리 → HTML 작성 → 파일 확인 → 요청받으면 배포.

### Skill

여러 작업에서 다시 쓸 절차와 확인 기준을 제공합니다.

매번 “없는 사실은 만들지 말기, 화면 확인하기…”를 반복해서 적는 부담을 줄입니다. 정해진 절차를 읽는 것이지 모델 가중치를 새로 학습시키는 것은 아닙니다.

이번 실습: brief-to-page: 입력 정리 → index.html → 화면·동작 확인.

### 도구 · Tool

파일 저장, 브라우저 열기, 팀 조회처럼 실제 기능을 실행합니다.

“저장했다”는 문장과 실제 파일 저장은 다릅니다. 실행 가능한 도구와 그 결과를 확인해야 합니다. 모든 도구가 MCP로 제공되는 것은 아닙니다.

이번 실습: 로컬 파일 도구는 HTML을 저장하고, Vercel 도구는 배포를 요청합니다.

### MCP

AI 앱과 외부 프로그램이 기능·입력·결과를 주고받는 공통 규칙입니다.

서로 다른 서비스도 정해진 형식으로 연결할 수 있게 합니다. MCP 자체가 답을 생각하거나 웹페이지를 호스팅하지는 않습니다.

이번 실습: ChatGPT의 MCP 클라이언트 ↔ Vercel MCP 서버.

### Vercel / 배포 결과

Vercel은 전달받은 파일을 배포하고 접속할 주소를 제공합니다.

Skill로 만든 파일과 Vercel에서 열린 웹페이지는 다른 결과물입니다. URL이 생긴 뒤에도 실제 화면을 확인합니다.

이번 실습: index.html은 파일, deployment ID는 배포 1회의 식별자, Preview URL은 그 결과를 여는 주소.

### 실행 흐름

- **1. 이번 요청 · 사용자 → ChatGPT**: 입력 A를 프롬프트로 전달합니다. 이름·제목·주제는 이번 작업의 재료입니다. 아직 파일이나 배포는 없습니다.
- **2. 절차 적용 · ChatGPT + Skill**: brief-to-page Skill을 읽어 어떤 순서와 기준으로 만들지 정합니다. 입력 B에도 같은 절차를 쓸 수 있습니다. Skill이 계정이나 배포 권한을 만들어 주지는 않습니다.
- **3. 파일 생성 · 에이전트 → 파일·브라우저 도구**: 에이전트가 사용 가능한 파일 도구로 index.html을 저장하고 브라우저로 확인합니다. 컴퓨터에 파일이 생겨도 아직 웹에 배포된 것은 아닙니다.
- **4. 외부 배포 · 앱의 MCP 클라이언트 ↔ Vercel MCP 서버 → Vercel**: 사용자가 배포를 요청하면 Vercel MCP 도구로 파일을 전달합니다. Vercel의 결과를 받아 URL을 확인합니다. 생성·연결·인증·배포·화면 확인은 각각 확인할 일입니다.

Skill 없이 MCP 도구를 쓸 수도 있고, MCP 없이 Skill로 글이나 파일을 만들 수도 있습니다. 이번 실습에서는 두 기능을 순서대로 연결합니다.

확인 질문: 소개 페이지의 문구를 정리하는 반복 절차를 재사용하고 싶다면 무엇을 먼저 만들까요?

정답: Skill — 반복할 작업 순서와 기준은 Skill에 담습니다. 외부 서비스 기능이 필요해질 때 MCP 연결을 추가합니다.

공식 안내: [OpenAI · Skills와 사용 방식](https://learn.chatgpt.com/docs/build-skills) · [MCP · 기본 구조](https://modelcontextprotocol.io/docs/learn/architecture)

## Skill은 “언제 쓰고, 어떻게 수행할지”를 담은 재사용 가능한 작업 묶음입니다.

이번에는 소개 글을 하나의 웹페이지로 바꾸는 brief-to-page를 만듭니다. 최소 구성은 SKILL.md 한 파일입니다. 이 파일은 실행 프로그램이 아니라 에이전트가 읽을 설명서입니다.

매뉴얼의 이름표(name), 적용 대상(description), 작업 순서(본문)를 나눠 생각하면 쉽습니다. 설명을 자세히 적어도 없는 도구·계정 권한이 자동으로 생기지는 않습니다.

### SKILL.md · 필수

Skill의 안내 정보와 실제 지침이 들어가는 중심 파일입니다.

Markdown은 제목·목록을 쓰는 텍스트 형식입니다. 맨 위 --- 사이의 YAML 머리말에는 이름·설명 같은 메타데이터를 적고, 그 아래에 작업 지침을 씁니다.

설명용 예시:

---
name: brief-to-page
description: 소개 글을 한 페이지 웹사이트로 만들 때 사용
---

# 작업 절차
1. 제공된 사실을 정리한다.
2. index.html을 만든다.
3. 화면과 동작을 확인한다.

이번 실습: 이번 실습은 이 파일만으로 구성하는 instruction-only 방식입니다.

### name · 이름

어떤 Skill인지 구별하고 이름으로 선택할 때 사용합니다.

이름만으로 기능이 구현되는 것은 아닙니다. 실제 기능은 아래 지침과 실행 가능한 도구에 달려 있습니다.

설명용 예시:

name: brief-to-page

이번 실습: @ 선택기에서 brief-to-page를 고릅니다.

### description · 적용 상황

어떤 요청에 이 Skill을 쓸지 판단하는 단서입니다.

무엇을 하는지, 언제 쓰는지, 어디까지 다루는지 적습니다. 홍보 문장보다 작업 범위가 중요합니다.

설명용 예시:

description: Turn a short public-facing brief into a responsive one-page static website.

이번 실습: 모임·프로젝트 소개 페이지에는 사용. 로그인·결제 앱에는 사용하지 않음.

### 본문 · 작업 순서와 기준

입력 읽기부터 결과 확인까지 실행할 절차를 설명합니다.

순서만 아니라 결과 형태와 완료 기준도 필요합니다. “예쁘게 만들기”보다 “index.html 1개, Topics 링크 확인”이 검토하기 쉽습니다.

설명용 예시:

## Procedure
- Use only supplied facts.
- Save one index.html.
- Check layout, links, and FAQ.
- Report checked / not checked.
- Do not deploy.

이번 실습: 입력 정리 → HTML/CSS 작성 → 실제 파일 열기 → 링크·FAQ 확인 → 결과 보고.

### scripts/ · 선택

반복 실행할 코드를 함께 둘 수 있습니다.

예를 들어 파일 형식을 검사하는 Python 코드를 둘 수 있습니다. 파일이 있다는 것과 코드가 실행됐다는 것은 다릅니다. 실행 도구와 환경이 필요합니다.

이번 실습: 이번 실습에는 없습니다. 설명만으로 가능한 작업부터 만듭니다.

### references/ · 선택

필요할 때 읽을 상세 자료를 둡니다.

긴 규칙이나 제품 용어집을 별도 파일로 분리할 수 있습니다. 본문에서 언제 어떤 자료를 읽을지 알려 줍니다.

이번 실습: 예: 회사 소개 문구 작성 규칙. 이번 실습에는 없습니다.

### assets/ · 선택

결과물을 만들 때 쓸 템플릿이나 이미지 등을 둡니다.

읽는 설명 자료와 출력에 활용할 재료를 구분합니다. 로고나 HTML 틀 같은 파일이 해당합니다.

이번 실습: 예: 승인된 로고, 페이지 템플릿. 이번 실습에는 없습니다.

### agents/openai.yaml · 선택

앱에서 보이는 이름·설명이나 도구 의존성 같은 추가 설정을 담을 수 있습니다.

최소 Skill에 필수인 파일은 아닙니다. 앱별 설정이며, 작성한다고 계정 인증이 완료되는 것도 아닙니다.

이번 실습: 이번 instruction-only 실습은 SKILL.md부터 이해하면 됩니다.

### 실행 흐름

- **1. 찾기 · name + description**: 어떤 Skill을 쓸지 이름과 적용 상황을 확인합니다. 이번에는 @로 직접 선택합니다. 설명은 선택의 단서입니다.
- **2. 읽기 · SKILL.md 본문**: 선택한 Skill의 전체 작업 지침을 읽고 이번 요청에 적용합니다. 본문은 작업 순서와 확인 기준입니다.
- **3. 필요할 때 더 보기 · 보조 자료·코드**: 지침에서 필요로 하는 참고 자료나 보조 코드를 사용합니다. 항상 모든 파일을 한꺼번에 읽는 것은 아닙니다. 이번 예시는 보조 파일 없이 진행합니다.

skill-creator는 Skill을 만드는 도우미이고, brief-to-page는 우리가 만들어 재사용할 Skill입니다. 입력 A/B는 작업 재료이고, index.html은 실행 결과입니다. 네 가지를 구분하세요.

확인 질문: description과 본문은 무엇이 다른가요?

정답: description은 적용 상황, 본문은 수행 절차 — 언제 이 Skill이 적절한지와, 선택한 뒤 어떻게 일할지를 구분하면 다른 입력에도 재사용하기 좋습니다.

공식 안내: [OpenAI · Skill 구성과 선택 방식](https://learn.chatgpt.com/docs/build-skills)

## MCP는 Model Context Protocol — AI 앱과 외부 기능을 연결하는 표준입니다.

“내 Vercel 팀을 조회해 줘”라는 말만으로 모델이 계정 정보를 알 수는 없습니다. 앱이 연결된 MCP 서버의 도구를 찾고, 필요한 입력을 보내고, 실제 결과를 받아야 합니다.

MCP는 직원과 외부 서비스가 주고받는 주문서·응답서의 공통 규격에 가깝습니다. 주소는 어디로 연결할지, 인증은 누구의 권한으로 사용할지, 도구 입력은 무엇을 할지 정합니다.

### Host · AI 앱

사용자 요청·모델·도구 연결을 함께 관리하는 앱입니다.

이번 실습의 호스트는 ChatGPT 앱입니다. Settings와 도구 실행 확인 화면도 이 앱에서 봅니다. 모델 자체와 앱은 구분합니다.

이번 실습: ChatGPT Work에서 “팀을 조회해 줘”라고 요청합니다.

### Client · 앱 안의 연결 담당

호스트 안에서 특정 MCP 서버와 요청·응답을 주고받습니다.

일반 학습자가 별도 클라이언트 프로그램을 작성할 필요는 없습니다. 앱이 서버별 연결을 관리합니다.

이번 실습: ChatGPT 안의 Vercel 연결 담당이 도구 요청을 전달합니다.

### Server · 기능 제공 프로그램

사용 가능한 도구의 설명과 입력 형식을 내보내고 호출을 처리합니다.

MCP 서버는 서버 컴퓨터 자체가 아니라 프로그램을 뜻합니다. 내 컴퓨터에서 실행될 수도 있고 서비스 업체가 원격으로 제공할 수도 있습니다.

이번 실습: 이번에는 Vercel이 제공하는 원격 MCP 서버에 연결합니다.

### Tool · 실행할 기능

서버가 공개한 작업 하나입니다. 이름·설명·입력 형식을 보고 호출합니다.

조회와 변경은 다른 도구입니다. “배포해 줘”라고 말해도 해당 도구가 연결·허용되어 있지 않으면 수행할 수 없습니다.

이번 실습: list_teams는 팀 조회, deploy_to_vercel은 파일 배포 요청입니다.

### Arguments / Result · 입력과 결과

도구에 전달할 구체적인 값과 실행 뒤 돌려받은 정보입니다.

입력 스키마는 필수 항목과 값의 형식을 정한 양식입니다. 결과에는 데이터뿐 아니라 실패 정보도 올 수 있습니다.

이번 실습: 배포 입력: 팀·프로젝트·파일·target. 결과 확인: 실제 배포 ID·상태·URL.

### Resources · 참고 데이터

서버가 읽을 수 있도록 제공하는 자료입니다.

실행을 요청하는 Tool과 달리, 앱이 작업에 참고할 내용을 가져오는 용도입니다. 제공 여부와 읽는 방식은 서버와 앱의 지원에 따라 다릅니다.

이번 실습: 일반적인 예: 문서 내용이나 데이터베이스 구조. 이번 Vercel 실습에서는 Tools를 사용하며 Resources가 있다고 가정하지 않습니다.

### Prompts · 서버의 요청 틀

서버가 제공하는 재사용 가능한 요청문 템플릿입니다.

사용자가 매번 직접 쓰는 일반 프롬프트와 달리 서버에서 제공하는 기능입니다. Skill처럼 폴더와 절차를 묶은 패키지와도 구분합니다.

이번 실습: 일반적인 예: 프로젝트 정보를 넣어 분석 요청을 만드는 틀. 이번 실습에서 복사하는 요청문은 이 사이트가 제공하는 일반 프롬프트입니다.

### Transport · 전달 방식

요청과 결과가 이동하는 통신 방식입니다.

Streamable HTTP는 HTTP를 사용하는 연결 방식입니다. STDIO는 내 컴퓨터에서 실행한 프로그램의 입력·출력으로 통신합니다.

이번 실습: Vercel 실습은 원격 주소에 연결하므로 Streamable HTTP를 고릅니다.

### OAuth · 계정 접근 허용

Vercel 로그인 화면에서 접근할 계정과 허용 범위를 확인합니다.

서버 주소를 입력한 것은 인증 완료가 아닙니다. 계정 연결, 개별 작업의 실행 확인, 실제 실행 성공도 서로 다릅니다.

이번 실습: Authenticate → Vercel 로그인·허용 → 앱으로 복귀 → 조회 도구 실행.

### 실행 흐름

- **1. 기능 찾기 · 앱의 Client ↔ MCP Server**: 앱이 사용할 수 있는 도구와 필요한 입력을 확인합니다. 없는 기능을 만들어 냈다고 가정하지 않습니다. 도구 이름·설명·입력 형식을 알게 됩니다.
- **2. 요청 구성 · 사용자 요청 → 도구 선택**: 에이전트가 “팀 조회”에 맞는 list_teams를 고릅니다. 배포라면 별도로 팀·파일 등 입력이 필요합니다. 일반 답변과 도구 호출은 다릅니다.
- **3. 실제 실행 · Client → Server → Vercel**: 앱이 연결과 권한을 확인해 요청을 보내면 서버가 Vercel 기능을 사용합니다. 필요한 확인 절차는 앱에서 진행합니다. 연결됨 표시만으로 이 단계가 성공한 것은 아닙니다.
- **4. 결과 읽기 · Vercel → Server → Client → 답변**: 돌아온 팀 목록이나 오류를 읽고 다음 행동을 정합니다. 배포 후에는 상태와 실제 URL의 화면도 따로 봅니다. 결과를 근거로 말하는지 호출 내역을 펼쳐 확인합니다.

MCP 서버가 제공할 수 있는 것은 Tools(실행 기능), Resources(참고 데이터), Prompts(요청 템플릿)입니다. 모든 서버가 세 가지를 모두 제공하지는 않습니다. 이번 Vercel 실습의 중심은 Tools입니다. 서버의 Prompts와 우리가 복사하는 일반 요청문, Skill 패키지도 같은 것은 아닙니다.

확인 질문: MCP에 연결됨이라고 표시되면 이미 웹페이지가 배포된 건가요?

정답: 아니요. 배포 도구 호출과 결과 확인이 따로 필요해요 — 연결은 통로를 준비한 상태입니다. 실제 파일과 대상이 들어간 배포 요청, 성공 상태, URL 확인이 이어져야 합니다.

## MCP 설정값의 역할

### Name · 연결 이름

앱 안에서 이 연결을 구별할 별명입니다.

vercel이라는 이름만 입력해서 연결되는 것은 아닙니다. 실제 연결 대상은 URL로 정합니다.

이번 실습: 여러 MCP를 연결했다면 이름으로 어느 서비스를 쓰는지 구분합니다.

### Type · 통신 방식

앱과 서버가 요청·응답을 전달할 방법입니다.

Streamable HTTP를 고르는 이유는 Vercel이 원격 HTTP 주소를 제공하기 때문입니다. 내 컴퓨터의 프로그램을 실행하는 STDIO와 다릅니다.

이번 실습: 이번 실습에서는 Streamable HTTP를 선택합니다.

### URL · MCP 서버 주소

앱이 도구 목록과 실행 요청을 보낼 주소입니다.

이 주소는 우리가 만들 웹페이지 주소가 아닙니다. 서버를 연결해도 아직 페이지를 배포한 것이 아닙니다.

이번 실습: https://mcp.vercel.com은 도구 연결 주소입니다.

### Authenticate · 계정 허용

어느 계정의 어떤 권한으로 기능을 사용할지 확인합니다.

Vercel 로그인 화면에서 계정과 접근 범위를 확인합니다. 로그인은 개별 배포 완료와는 별개입니다.

이번 실습: 인증 후 팀 조회 도구를 실행해 실제 접근 가능한 팀을 확인합니다.

### /mcp · 연결 상태

앱에서 설정된 MCP 연결 상태를 확인하는 명령입니다.

연결 상태는 통로의 상태입니다. 실제 조회 결과나 배포 상태는 해당 도구 실행으로 확인합니다.

이번 실습: 연결됨 → 팀 조회 성공 → 배포 성공을 따로 확인합니다.

## 배포 입력과 결과의 역할

### teamId · 소유 팀

누구의 작업 공간에 배포할지 정합니다.

ID는 팀을 구별하는 값이고, slug는 주소 등에 쓰는 짧은 이름입니다. 임의의 예시 값이 아니라 조회된 값을 씁니다.

이번 실습: 팀 조회 결과를 아래 팀 ID 또는 slug 칸에 입력합니다.

### name · 프로젝트

하나의 사이트를 관리하는 묶음의 이름입니다.

프로젝트 하나에 여러 배포 버전이 생길 수 있습니다. 처음에는 새 이름을 쓰고 수정 배포는 같은 프로젝트에 합니다.

이번 실습: 같은 프로젝트 → 처음 만든 배포 → 제목을 바꾼 새 배포.

### files · 실제 파일

배포할 파일의 경로와 전체 내용을 전달합니다.

파일 이름이나 내 컴퓨터 경로만 알려 주는 것으로는 부족합니다. file은 상대 경로, data는 내용, encoding은 내용을 표현한 방식입니다.

이번 실습: index.html: HTML은 내용·구조, CSS는 모양, JavaScript는 필요한 동작을 담당합니다. 이번 페이지는 CSS를 HTML 안에 넣습니다.

### target · 배포 용도

preview는 검토용, production은 정식 서비스용으로 구분합니다.

Preview도 실제 서버에 올라간 결과입니다. 검토용이라고 반드시 본인만 볼 수 있거나, production이라고 반드시 누구나 볼 수 있는 것은 아닙니다.

이번 실습: 이번 필수 실습은 preview입니다. 접근 가능 여부는 URL에서 따로 확인합니다.

### ID · 상태 · URL

배포 1회를 구분하고 결과를 확인하는 정보입니다.

deployment ID는 배포 식별자, 상태는 진행·성공·실패 여부, URL은 결과를 열 주소입니다. 프로젝트 이름과 배포 ID는 다릅니다.

이번 실습: 상태 성공 → URL 열기 → 제목·링크·FAQ 동작 확인. 수정 후에는 새 배포 결과를 봅니다.

## 따라하기

1. **Skill 만들기** — PROMPTS의 1번과 EXAMPLES의 Skill 본문을 함께 입력합니다. `brief-to-page`가 Skills 목록에 나타나는지 확인합니다. 예시 텍스트를 첨부한 것만으로 설치된 Skill은 아닙니다.
2. **Skill 사용하기** — `@` 선택기에서 실제 Skill을 고른 뒤 2번과 입력 A를 전달합니다. 생성된 `index.html`을 열고 Topics 링크와 FAQ를 직접 사용합니다.
3. **반복해보기** — 새 작업/폴더에서 같은 Skill에 입력 B를 줍니다. A의 이름·문구가 B에 섞이지 않는지 확인합니다. 배포할 때는 다시 A 작업으로 돌아옵니다.
4. **MCP 연결하기** — 아래 설정을 저장하고 Restart, 이어서 Authenticate로 로그인합니다. `/mcp`에서 연결 상태를 확인합니다.
5. **도구 사용 확인하기** — 4번 요청으로 Vercel 문서를 조회합니다. 이어 5번 요청으로 팀/프로젝트 목록을 확인하고, 배포할 팀을 지정합니다. 도구 호출이 없으면 연결 성공으로 기록하지 않습니다.
6. **Preview 배포하기** — 6번 요청의 `<TEAM>`과 `<PROJECT_NAME>`을 실제 값으로 바꿉니다. 다른 프로젝트와 겹치지 않는 새 이름을 사용합니다. 파일 목록과 target을 검토하고 도구 실행을 승인합니다.
7. **결과 확인하기** — 7번 요청 후 실제 URL을 엽니다. 배포 상태, 제목, 링크, FAQ, 좁은 화면을 확인합니다. Preview가 로그인 화면을 보이면 보호 설정인지 확인합니다. 보호를 무조건 끄지 않습니다.
8. **한 가지만 바꾸기** — 8번 요청으로 제목을 바꾸고 같은 프로젝트에 새 Preview를 만듭니다. 새 URL에서 변경을 확인합니다. 이전 배포 URL과 혼동하지 않습니다.
9. **선택: 공개 게시** — 누구나 접근하는 정식 URL이 필요하면 9번 요청을 사용합니다. 검토한 파일을 production으로 배포하고 실제 접근 범위를 별도로 확인합니다.

## 막히면

- **Skill이 안 보임:** Skills 목록, 작업 폴더, 생성 위치를 확인하고 앱을 다시 시작합니다. 단순 채팅에 본문을 붙여넣은 것은 재사용 Skill 설치와 구분합니다.
- **MCP 로그인 실패:** 서버 URL·Authenticate 상태·선택한 Vercel 계정/팀을 확인합니다. 채팅으로 인증 토큰을 전달하지 않습니다.
- **배포 도구가 없음:** 연결 서버의 도구 목록을 다시 확인합니다. 파일을 만들었다는 답변을 배포 완료로 해석하지 않습니다. PROMPTS의 10번으로 실제 상태를 기록합니다.
- **빌드 실패:** 배포 ID를 대상으로 빌드 로그를 읽고 해당 오류만 수정합니다. 통째로 재작성하지 않습니다.
- **주소는 있는데 화면이 다름:** 최신 deployment ID/URL, 파일 내용, Preview 보호/로그인 상태를 확인합니다.
